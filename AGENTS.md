## Token Efficiency

- Be concise. Prefer short, actionable output over verbose explanations.
- Don't dump full file contents. Read only what's needed, use targeted searches.
- Don't repeat context or restate what's already in the conversation.
- Skip preamble and postamble. Answer directly, without "Based on the information provided..." or "Here is what I will do next...".
- One-word or short-paragraph answers are preferred over long explanations.
- Don't ask unnecessary questions. Use the tools provided to answer questions that can be answered without the user.
- Don't read large files in full. Use grep for specific content, read targeted sections with offset/limit.
- Don't load skills unless the task matches their description. A skill's SKILL.md is only loaded when triggered by a matching task.
- Prefer editing existing files over creating new ones. Never create documentation files unless explicitly requested.
- Don't commit changes unless explicitly asked.
- Don't add comments to code unless asked.
- Don't use emojis unless explicitly requested.
- Always respond in Russian unless explicitly requested otherwise.

## Code Style

- Follow existing code conventions. Check neighboring files before writing.
- Never introduce code that exposes or logs secrets.
- When identifying new critical security risks, vulnerabilities, or changed protection requirements, update `docs/security.md`.
- Never use `Telegram.WebApp.showPopup(...)`, native browser popups, alerts or dialogs (`confirm()`, `alert()`, `prompt()`). For modal windows always use the project's internal component (`@component('tma.partials.modal')`) with Alpine.js state; for confirmation prompts always use `await window.confirmDialog({ title, message, confirmText, cancelText, variant })`.
- **Form & Action Loading States**: Every asynchronous UI action (creating, editing, deleting, status changing, bulk operations) MUST display explicit loading feedback: disable the trigger/submit button (`:disabled`), update button text (e.g. `Создание...`, `Сохранение...`, `Удаление...`) or show a spinner, and never close confirmation modals before the server request completes.
- All API pagination must be strictly protected against unbounded limits: always clamp `per_page` between 1 and 100 (`min(max((int) $request->query('per_page', $default), 1), 100)`).
- **Search Engine Anti-Indexing (Strict Noindex)**: All pages, views, documents, and assets must be completely hidden from search engine robots. Any new or modified HTML/Blade layout must contain `<meta name="robots" content="noindex, nofollow, noarchive, nosnippet">`. All HTTP responses must include `X-Robots-Tag: noindex, nofollow, noarchive, nosnippet`. `public/robots.txt` must always disallow all crawlers (`User-agent: *`, `Disallow: /`). Nginx FastCGI must maintain `fastcgi_hide_header X-Robots-Tag;` to avoid header duplication.

## Code Commenting Guidelines

When writing or editing code, **never** leave typical AI-generated ("machine") comments:

1. **No ASCII/Unicode section banners or dividers**:
   - Do NOT use `// ====...`, `// ────...`, `// ----...`, `/* ====... */`, or `<!-- ────... -->` banners.
   - Instead, use a single concise comment line (e.g., `// Tag color palette and badge helpers`) or let clear function/module structure speak for itself.

2. **No numbered step-by-step narration**:
   - Do NOT add sequential step comments like `// 1. Validate input`, `// 2. Fetch data`, `// 3. Return result`.
   - Do NOT label UI or code sections with artificial markers like `Zone 1`, `Zone 2`, `TAB 1`, or arrows (`→` / `->`) in comment headers.

3. **No obvious or redundant comments**:
   - Do NOT state what the code already clearly expresses (e.g., `// Focus input`, `// Clear button`, `// Singleton instance`, `// Init`, `<!-- Generated by JS -->`).
   - Write comments only when needed to explain non-obvious business logic, edge cases, or brief section purposes, keeping them natural and concise.

## Environment & Database Safety

- The application runs in Docker containers. PHP, Artisan, and Composer commands must be executed inside the `crm_app` container: `docker exec crm_app <command>` (e.g., `docker exec crm_app php artisan ...`).
- Key containers: `crm_app` (PHP/Laravel), `crm_nginx` (web server), `crm_postgres` (PostgreSQL), `crm_redis` (Redis), `crm_queue` (queue worker).
- **STRICT PROHIBITION OF DESTRUCTIVE OPERATIONS AND DANGEROUS TESTS WITHOUT APPROVAL**:
  - **Strictly forbidden** to run potentially destructive tests (backup restoration tests like `RestoreBackupCommandTest`, emergency wipe tests like `EmergencyWipe*`, schema or table wipes like `wipeTables`, or migration resets) **without explicit prior user approval**.
  - **Strictly forbidden** to execute destructive database commands (`backup:restore`, `migrate:fresh`, `db:wipe`, `migrate:reset`, `emergency-wipe`, `DROP SCHEMA`, `DROP DATABASE`) without explicit prior confirmation from the user.
  - **Strictly forbidden** to invoke Artisan commands directly via `php -r` in working/production environments (`crm` / `dev` / `production`).
  - When running tests, always prefer targeted test files for the specific feature under development (e.g., `php artisan test tests/Feature/Orders/...`). Full test runs must never execute tests that drop or overwrite database schemas.

## Git Workflow

- Never commit directly to `main` when implementing features or bug fixes.
- Development must be done in separate feature/fix branches (`feat/...`, `fix/...`).
- When merging into `main`, always use squash merge (`git merge --squash <branch>`), create a single concise conventional commit in `main`, and delete the working branch.
- Version releases must use annotated tags (`git tag -a vMAJOR.MINOR.PATCH -m "..."`).
