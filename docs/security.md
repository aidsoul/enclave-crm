# Чеклист безопасности и критические точки перед деплоем

## 1. Конфигурация окружения (.env)
- [ ] **Режим отладки отключен**: `APP_DEBUG=false`. При `true` любая ошибка раскрывает стек вызовов, переменные окружения и ключи БД.
- [ ] **Окружение продакшена**: `APP_ENV=production`.
- [ ] **Ключ приложения**: `APP_KEY` сгенерирован заново для продакшена и хранится в секрете.
- [ ] **Файлы секретов**: `.env` и дампы БД никогда не коммитятся в git (проверено в `.gitignore`).

## 2. Сетевая безопасность и шифрование (TLS / HTTPS)
- [ ] **HTTPS / SSL**: Контейнер `crm_nginx` слушает HTTP (`80`). На продакшене перед ним обязателен обратный прокси (Nginx/Traefik/Cloudflare/Caddy) с SSL-сертификатом. Без HTTPS токены Telegram, сессионные куки и данные клиентов передаются в открытом виде.
- [ ] **Изоляция служебных портов**: Порты PostgreSQL (`5432`), Redis (`6379`) и Reverb (`6001`) должны быть привязаны строго к `127.0.0.1` или находиться во внутренней сети Docker, без публичного доступа из интернета.

## 3. Telegram бот и Mini App (TMA)
- [x] **Секретный токен вебхука**: Для маршрута вебхука бота настроена обязательная проверка заголовка `X-Telegram-Bot-Api-Secret-Token` (`TelegramController@webhook`). Запросы без заголовка, с несовпадающим токеном или при ненастроенном секрете отклоняются с кодом `401 Unauthorized` и логированием в канал `webhooks`. В команду `telegram:set-webhook` внедрена обязательная передача токена в Telegram Bot API: команда валидирует формат токена (1-256 символов `[A-Za-z0-9_-]`), блокирует вызов без токена как в проде, так и в локальном окружении, и передает токен в метод `setWebhook(..., secret_token: $secretToken)`.
- [x] **Валидация initData**: Все запросы от Mini App проходят строгую проверку HMAC-SHA256 подписи с использованием `BOT_TOKEN` в сервисе `TelegramInitDataValidator`:
  - **Криптографическая верификация HMAC-SHA256**: Вычисление секретного ключа `hash_hmac('sha256', $token, 'WebAppData', true)` и подписи от отсортированной строки параметров (`data_check_string`) с постоянным временем сравнения через `hash_equals()`, полностью устраняющим уязвимости side-channel тайминг-атак.
  - **Целостность и валидация параметров**: Сохранение нулевых и строковых значений (`'0'`, falsy) без искажения или потери данных, обязательная проверка формата хеша (64 hex-символа), обязательное наличие и числовая валидация `auth_date`.
  - **Защита от Replay и манипуляций со временем**: Проверка устаревания `initData` по TTL (`services.telegram.init_data_ttl`, по умолчанию 1 час) и блокировка меток времени из будущего с допустимым дрейфом часов до 120 секунд.
  - **Кэширование результата валидации**: Устранение повторных криптографических вычислений при последовательном извлечении пользователя и ID в рамках одного запроса.
  - **Изоляция сессий и шлюз Mini App**: Авторизация в CRM выполняется строго через эндпоинты `/api/auth/tma` и `/api/invitations/accept` с валидацией подписи `initData` и генерацией защищенного сессионного токена с привязкой к IP и 2FA облачным паролем.
- [x] **Безопасность сессий TMA и защита от кражи токенов (Token Theft & IP Verification)**:
  - **Привязка сессий к проверенным IP и геолокация**: При авторизации пользователя (TMA, desktop link, invitations) фиксируются начальный IP клиента (`CF-Connecting-IP`, `X-Forwarded-For`, `$request->ip()`) и страна подключения (`CF-IPCountry`, `X-Country-Code`, GeoIP resolver). В Redis создается белый список `verified_ips`.
  - **Облачный пароль (Cloud Password / 2FA)**: Для максимальной защиты аккаунта от кражи сессионных токенов и взлома Telegram используется персональный облачный пароль пользователя (хешируется с помощью `Hash::make()` в `cloud_password_hash`). При входе с нового IP-адреса доступ блокируется (`403 Forbidden` / `ip_verification_required`), пока пользователь не введет свой облачный пароль. Если пароль еще не задан, система принудительно требует его установить (`setupCloudPassword`).
  - **Защита от подбора пароля (Brute-force protection)**: При вводе неверного облачного пароля ведется атомарный счетчик попыток в Redis. При превышении лимита (по умолчанию 3 попытки) IP временно блокируется на 15 минут, а владельцу отправляется предупреждение о подозрительной активности.
  - **Административный сброс пароля**: Владелец (Owner) CRM имеет возможность сбросить облачный пароль скомпрометированного или забывшего пароль сотрудника (`POST /api/admin/users/{user}/reset-cloud-password`) с обязательным аудитом в `action_logs`.
  - **Оповещение в Telegram-бот и экстренная блокировка**: При входе с нового IP Telegram-бот отправляет информационное уведомление с IP, страной, устройством и компактной кнопкой [🚨 Заблокировать сессию] (`sec_blk:{hash}` до 40 байт, с гарантией соблюдения 64-байтового лимита Telegram Bot API). При нажатии кнопки сессия мгновенно аннулируется, а подозрительный IP отправляется в блокировку на 1 час. Все события логируются в `action_logs` (`ActionType::AUTH`).
- [x] **Защита веб-маршрутов TMA**: Неавторизованные не-JSON запросы к маршрутам TMA блокируются или перенаправляются на страницу ошибки (`/blocked`, HTTP 403), исключая рендеринг внутренней разметки для гостей. На публичных точках входа (`/`, `/tma`) неавторизованным гостям отдаётся нейтральный контейнер-загрузчик `tma.auth.entry` без элементов разметки CRM, который проверяет наличие Telegram WebApp окружения и перенаправляет неавторизованных посетителей на страницу 403 (`/blocked`), а вложенные приватные маршруты защищены на уровне middleware `ValidateTmaUser`.

## 4. Входящие API заказов и лидов
- [x] **Токены сайтов (Site Tokens)**: Обязательная проверка валидности и активности токена источника перед созданием лида или заказа.
- [x] **Валидация формата токенов сайтов**: Добавлена проверка `Str::isUuid($token)` перед выполнением запроса к базе данных, предотвращающая фатальные ошибки PostgreSQL (SQLSTATE 22P02 invalid input syntax for type uuid) при передаче некорректного токена.
- [x] **Rate Limiting**: Ограничение частоты запросов на эндпоинты `/api/v1/orders/incoming` и `/api/v1/leads/incoming` для защиты от флуда и DoS.
- [x] **Антифрод и защита от спам-атак на вебхуки лидов и заказов (Leads & Orders Anti-Fraud & Fingerprinting)**:
  - **Многоуровневый Rate Limiting**: Комплексная защита эндпоинтов `/api/leads/incoming` и `/api/orders/incoming` на уровнях: 1) по токену сайта (60 req/min), 2) по IP клиента (15 req/min), 3) по цифровому отпечатку браузера/устройства (10 req/min), 4) по контакту телефона/email для лидов (5 req/min). Предотвращает DoS, исчерпание лимитов сайта одним клиентом и атаки типа SMS/call-bombing.
  - **Fingerprinting (Цифровой отпечаток клиента)**: Извлечение и валидация IP клиента (`client_ip`, заголовок `CF-Connecting-IP`, `X-Forwarded-For`), User-Agent, Accept-Language, а также клиентского отпечатка (`fingerprint` / `visitor_id` / `X-Client-Fingerprint`). При отсутствии явного отпечатка генерируется детерминированный SHA-256 хеш комбинации сетевых параметров. Данные телеметрии сохраняются в `extra_data['_antifraud']` сущности.
  - **Honeypot-ловушки**: Мониторинг скрытых служебных полей формы (`_honey`, `website`, `hp_comment`, `address_line2`, `fax`, `company_fax`). При их заполнении ботом запрос мгновенно отсекается со 100% спам-рейтингом.
  - **Эвристики спама и ботов**: Автоматическое распознавание спам-скриптов и сканеров по сигнатурам User-Agent, детекция временных/одноразовых email-доменов (mailinator, tempmail и др.), проверка фиктивных номеров телефонов (повторяющиеся цифры, последовательности, невалидная длина), защита от ротации номеров с одного устройства (атаки SMS-бомбинга), фильтрация спам-ссылок и HTML/BBCode в полях имени и сообщения.
  - **Подавление уведомлений и изоляция очередей**: Заблокированные сущности возвращают 202 с флагом `spam: true`, не загружая фоновые очереди `high` и полностью исключая ложные срабатывания в Telegram-чатах персонала. Заказы и заявки с промежуточным риском сохраняются в CRM с пометкой подозрительности, блокируя отправку тревожных уведомлений персоналу.
- [x] **Защита от Race Condition при повторной доставке вебхуков**: Составной частичный уникальный индекс `orders_site_external_id_active_unique` на `(site_id, external_id)` для всех незавершенных закасов (`status != 'completed'`) в сочетании с атомарным Redis-локом по `external_id` в очереди `ProcessIncomingOrderJob`, исключающий дублирование заказов при параллельных вызовах.
- [x] **Защита от Race Condition при повторной доставке лидов (Leads)**: Составной уникальный частичный индекс `leads_site_external_id_unique` на `(site_id, external_id)` в сочетании с приоритетной распределенной блокировкой по `external_id` и перехватом коллизий уникальности в `ProcessIncomingLeadJob`.
- [x] **Атомарность разрешения покупателей по email**: Поиск и обновление клиентов без номера телефона выполняются с блокировкой `lockForUpdate()`, а коллизии дублирования при параллельном создании перехватываются на уровне `CustomerResolver`.
- [ ] **Белый список IP**: По возможности настроить фильтрацию разрешенных IP-адресов интернет-магазинов или CMS.

## 5. Доступ и данные
- [x] **Ограничение пагинации**: Всегда удерживать лимит `per_page` в диапазоне 1–100 (`min(max((int) $request->query('per_page', $default), 1), 100)`).
- [ ] **RBAC и Policies**: Проверка политик `can:update,order`, `can:cancel,order` и ролей на всех деструктивных маршрутах.
- [x] **Изоляция финансовых данных каталога и карточки товара**: Себестоимость (`cost_price`) и маржа в `ProductResource` и `OrderResource`, а также доступ к полной карточке товара (`/api/products/{product}`) закрыты от курьеров и внешних API клиентов (`role:owner,manager` строго). Себестоимость и маржа принудительно обнуляются (`null`) для любых неавторизованных в CRM запросов.
- [x] **Безопасная архивация каталога**: При удалении товара через API каталога или синхронизацию, операция выполняется внутри `DB::transaction` с пессимистичной блокировкой `lockForUpdate()`. Если товар используется в заказах, выполняется каскадная архивация (`is_active = false`) товара и вариантов без физического удаления, сохраняя целостность заказов и исключая состояние гонки.
- [x] **Строгая валидация конечного автомата статусов (OrderStatusMachine)**: Все методы смены статуса (включая общий `changeStatus` и `markComplete`) принудительно валидируют разрешенные переходы `getAvailableStatuses()` и блокируют перевод в `completed` ценных отправлений без цифровой подписи клиента.
- [x] **Безопасная загрузка фотофиксации вручения курьером**: Загрузка фото ограничена валидацией MIME-типов (JPEG, PNG, WEBP, HEIC), размера (до 10 МБ) и максимального разрешения (`dimensions:max_width=8192,max_height=8192` для защиты от пиксельных декомпрессионных бомб / DoS). Реализована дедупликация по SHA-1 хешу содержимого файлов: сервер отсекает одинаковые изображения как в загружаемой пачке, так и относительно уже сохраненных снимков заказа. Сохранение фото и обновление строки доставки выполняются внутри `DB::transaction` с пессимистичной блокировкой `lockForUpdate()`, исключая состояние гонки (Race Condition) при параллельных запросах. Расширения файлов принудительно определяются сервером через `$file->guessExtension()` на основе содержимого, исключая манипуляции с именами. Имена файлов генерируются случайно через UUID/хэш во избежание path traversal. Доступ к загрузке и удалению строго ограничен назначенным курьером, ответственным менеджером или владельцем через политику `OrderPolicy@uploadProof`, при этом запрещена модификация отмененных заказов. Добавлен Rate Limiting (`throttle:30,1`) для предотвращения флуда и исчерпания дискового пространства. В конфигурации Nginx каталог `/storage/` защищен от исполнения PHP-скриптов (`deny all` для `\.php$`), а заголовок `Permissions-Policy` сконфигурирован с `camera=(self 'https://web.telegram.org')` для безопасной работы видоискателя камеры смартфона. При замене, ротации (`DataRetentionService`) или экстренном удалении данных (`Emergency Wipe`) файлы фотофиксаций удаляются из файлового хранилища.
- [x] **Безопасная обработка и хранение цифровой подписи клиента (HTML5 Canvas)**:
  - **Валидация файлов и защита от атак**: Строгая проверка в `UploadDeliverySignatureRequest` (MIME-типы `image/png`, `image/webp`, макс. 1024 КБ, лимит размеров `max_width=4096,max_height=4096` против декомпрессионных бомб). Имена файлов генерируются сервером (`sig_{order_id}_{random}.png`), исключая Path Traversal.
  - **Транзакционность и атомарная замена**: Сохранение в БД обёрнуто в `DB::transaction`. При ошибке БД вновь загруженный файл немедленно удаляется из файловой системы. Старый файл подписи стирается с диска строго после успешного коммита транзакции.
  - **Разграничение доступа (RBAC)**: Загрузка и перезапись разрешены только назначенному курьеру (до завершения заказа) или владельцу (`OrderPolicy@uploadSignature`). Удаление подписи разрешено исключительно владельцу системы (`OrderPolicy@deleteSignature`), курьеры и менеджеры лишены права удаления. Для отменённых заказов любые манипуляции с подписью запрещены. Маршруты защищены rate limiting (`throttle:30,1`).
  - **Защита от спуфинга на Canvas**: Проверка минимального количества точек (min 12) и габаритов подписи (bounding box не менее 15px), исключающая случайные нажатия/точки. Экспорт с принудительным белым фоном (`#ffffff`) и очистка canvas-буферов для предотвращения утечек памяти в WebView.
  - **Блокировка завершения ценных заказов**: Заказы с `is_valuable` или превышающие порог стоимости не могут быть переведены в статус `completed` без сохранённой подписи.
  - **Очистка данных**: Подписи очищаются при каскадном удалении заказов, плановой ротации (`DataRetentionService`) и экстренном уничтожении данных (`PanicService`).
- [x] **Санитизация экспорта (CSV Injection)**: Экранирование спецсимволов (`=`, `+`, `-`, `@`) в текстовых полях экспорта во избежание выполнения формул в табличных процессорах.
- [x] **Защита от Token Replay и состояния гонки при входе с ПК**: Одноразовый токен авторизации на десктопе утилизируется атомарной операцией `Redis::getdel`.
- [ ] **Резервное копирование**: Настроено автоматическое резервное копирование PostgreSQL и медиа-файлов хранилища (`storage/app`) в защищенное удаленное хранилище (S3/R2).

## 6. Docker и инфраструктура контейнеров
- [x] **Отключение Vite Dev-сервера в проде**: Контейнер `node` с открытым портом `5173` вынесен под профиль `dev` в `docker-compose.yml` и исключен из `docker-compose.prod.yml`. В продакшене фронтенд собирается статически (`npm run build`), а Nginx использует конфигурацию `docker/nginx/prod.conf`.
- [x] **Пароль на Redis**: В `docker-compose.prod.yml` добавлена поддержка аутентификации через `REDIS_PASSWORD` с автоматической активацией `--requirepass` и защищенным healthcheck.
- [x] **Хеширование токенов сайтов (`api_token`)**: В таблице `sites` колонка `api_token` заменена на `api_token_hash` (`varchar(64)` с уникальным индексом). Открытые токены никогда не сохраняются в базе данных. Проверка входящих вебхуков (`/api/orders/incoming`, `/api/leads/incoming`, `/api/catalog/sync`) осуществляется исключительно по SHA-256 хешу переданного токена (`Site::findByTokenCached()`). При создании и ротации токена открытый ключ (`UUID`) возвращается клиенту однократно (по аналогии с GitHub/Stripe), а в интерфейсе отображается статус защиты и замаскированное значение. Прямая передача SHA-256 хеша в заголовках отклоняется (`pass-the-hash` защита). При дампе БД токены сайтов не могут быть скомпрометированы.
- [x] **Защита экстренного уничтожения данных (Wipe PIN)**: Ограничение перебора PIN-кода на уровне 10 запросов в минуту сопровождается атомарным инкрементом счетчика попыток и временной блокировкой на 15 минут после 5 неверных попыток. В список очищаемых таблиц включены `product_variants`.
- [x] **Изоляция чата заказа и защита контактных данных менеджеров (Order Chat System)**:
  - **Анонимизация и сокрытие контактов менеджера**: В канале общения с водителем (`courier`) личные контактные данные менеджеров (номер телефона, личный Telegram ID, никнейм и email) никогда не передаются на сторону клиента. В API ресурсах (`OrderMessageResource`) и событиях WebSockets (`OrderMessageSent`) отправитель маскируется под обезличенным именем `Менеджер`.
  - **Строгое разделение каналов**: Внутренний чат команды (`internal`) физически заблокирован для роли курьера на уровне Policy, FormRequest и WebSocket-авторизации каналов (`routes/channels.php`). Курьер получает `403 Forbidden` при любой попытке чтения или отправки сообщений в `internal`.
  - **Ограничение доступа к заказам**: Курьер авторизуется для чата строго по тем заказам, где он назначен исполнителем.
  - **Безопасность вложений и клиентское сжатие**: Валидация изображений (JPEG, PNG, WEBP), генерация случайных имен файлов, изоляция директорий `chat/{order_id}/`. Клиентское сжатие через Canvas (до 1920x1920px, 82% quality) предотвращает перегрузку сети и хранилища.
  - **Персистентность медиафайлов**: Каталог `storage/app/public` смонтирован напрямую с хоста, что предотвращает потерю пользовательских файлов (подписей, фотоотчетов и вложений чата) при перезапуске, пересоздании контейнеров Docker или очистке анонимных томов.
  - **Контроль редактирования и удаления сообщений (RBAC & Time-Window)**: Владелец имеет полные права на редактирование и удаление любого сообщения в чате заказа. Менеджер может редактировать только собственные сообщения в течение 10 минут с момента отправки (после истечения 10 минут редактирование блокируется с `403 Forbidden`), удаление сообщений для менеджеров полностью запрещено. Курьер не имеет прав на редактирование или удаление сообщений (`403 Forbidden`).
  - **Обязательный аудит мутаций чата**: Любое редактирование или удаление сообщения чата обязательно логируется в `action_logs` (`ActionType::UPDATE` / `ActionType::DELETE`, `field_name: chat_message`) с сохранением старого и нового текста, автора действия, IP и User-Agent.
  - **Очистка данных и паника**: Сообщения и вложения чата полностью очищаются при экстренном стирании (`Emergency Wipe`), каскадном удалении заказов и автоматической ротации (`DataRetentionService`).
  - **Rate Limiting и защита от флуда**: Отправка сообщений ограничена `throttle:60,1`. Пагинация защищена курсорным ограничением (`limit` от 1 до 50).
- [x] **Полное уничтожение бэкапов при экстренной очистке (Emergency Wipe)**: Реализована опция удаления всех локальных архивов и дампов, а также бэкапов в S3-хранилище через фоновый Job `PurgeAllBackupsJob` с наивысшим приоритетом (`high`), исключающая возможность восстановления данных после срабатывания кнопки паники.

## 7. Аудит безопасности и журналирование действий пользователей
- [x] **Фиксация действий аутентификации и сессий**: Все входы (TMA, desktop), создание ссылок входа, выходы и отзывы активных сессий фиксируются в `action_logs` (`ActionType::AUTH`).
- [x] **Аудит экспорта данных**: Финансовые выгрузки в CSV фиксируются в `action_logs` (`ActionType::EXPORT`) с сохранением диапазона дат, site_id, количества строк.
- [x] **Фиксация сетевого контекста (IP и User-Agent)**: Все записи аудита обогащены полями `ip_address` и `user_agent` инициатора.
- [x] **Покрытие мутаций товаров и персонала**: Вариации товаров (`ProductVariantObserver`) и изменения профилей пользователей (`UserObserver`) полностью аудируются при создании, редактировании и удалении.
- [x] **Аудит пользовательских настроек**: Изменения пользовательских настроек (`scope === 'user'`) фиксируются в аудите с привязкой к `target_user_id`.
